Scaling multi-subject filters
for pull consumers

Why filtering on 10, 30, 50 or 90 subjects used to fall off a cliff — and how batching the store lookup makes per-message delivery cost flat instead of growing with the number of filters.

branch: claude/better-multi-filter-v0qig filestore · memstore · consumer +469 / −2 lines 16×–125× faster

01The symptom

A JetStream pull consumer can filter the stream by a set of subjects. Operators reported that as the filter set grew — 10, 30, 50, 90 subjects — delivery throughput dropped sharply and latency rose. In the worst cases it was faster to remove the filter entirely, push every message over the network, and let the client throw away what it didn't want.

The tell. The hot path was calling LoadNextMsgMulti once per delivered message. The cost of that one call grows with the number of filter subjects, so total delivery cost scaled like messages × filters instead of just messages.

02How delivery worked (before)

The consumer's delivery loop, loopAndGatherMsgs, pulls exactly one message per iteration via getNextMsg. For a multi-filtered consumer that meant one store call — LoadNextMsgMulti — for every single message:

loopAndGatherMsgs1 msg / iteration
→
getNextMsgholds o.mu
→
LoadNextMsgMultionce per message

Every call starts from scratch — it keeps no memory of where the previous match was.

Inside that one call, the store does real work every time:

  • re-acquire the store read lock (fs.mu.RLock);
  • re-select the starting message block from the cursor (selectMsgBlockWithIndex);
  • walk the block's per-subject tree (fss) and intersect it against the sublist of filter subjects (IntersectGSL) — or linearly scan the block — just to locate the single next match, then return.

That intersection / scan is the part whose cost rises with the number of filter subjects and the number of distinct subjects in the block. Doing it per message is the bottleneck.

memstore was worse. Its LoadNextMsgMulti was an explicit "simple linear walk to get started" — a full scan from the cursor with no subject-index acceleration at all. Sparse matches on a memory stream degrade toward O(M²) across a delivery.

03The idea: amortize the search

The expensive thing is searching for matches; the cheap thing is reading a message by sequence. The fix decouples them: do the multi-subject search once per batch, remember the matching sequence numbers, then serve those sequences with plain, cheap lookups.

getNextMsg
→
prefetch buffermatching seqs
→
LoadMsg(seq)fresh, by sequence
buffer empty?
→
LoadNextMsgsMultisearch once · fills up to 256 seqs

So in steady state, delivering a message costs one LoadMsg by sequence — the same as the no-filter baseline operators already found acceptable. The multi-subject search happens roughly once every 256 messages instead of every message.

Why prefetch sequences, not message bodies?

Prefetching whole messages would risk delivering a message that was acked or removed in the window between prefetch and delivery. Prefetching only the matching sequence numbers keeps the body load lazy and fresh: if a message disappeared after prefetch, its LoadMsg simply fails and the consumer skips it. Sequences in NATS are immutable — a sequence maps to one message forever or to nothing — so a buffered sequence can never point at the wrong message.

04What changed, concretely

Store engine — a batched API

A new method on the store interface gathers many matches per call:

// Append up to maxSeqs matching sequences (ascending) at or after start.
func LoadNextMsgsMulti(sl *gsl.SimpleSublist, start uint64,
        maxSeqs int, seqs *[]uint64) (n int, last uint64, err error)
  • filestore.go LoadNextMsgsMulti reuses the existing psim block-skipping to jump to the first block that can contain a match, then msgBlock.collectMatchingMulti gathers all the block's matches in a single sequential pass — instead of one intersection per message.
  • memstore.go LoadNextMsgMulti now narrows the scan using the fss subject tree (computing the lowest matching First across matched subjects), and the batched LoadNextMsgsMulti is added alongside it.
  • store.go the method is added to the StreamStore interface.

Consumer — a prefetch buffer

consumer.go getNextMultiFiltered replaces the per-message LoadNextMsgMulti call. It mirrors that method's contract exactly (same EOF semantics, same cursor advancement) so the surrounding delivery, skip and num-pending logic is untouched:

if o.sseq <= o.mflast {           // rewound (e.g. redelivery retry) → buffer is stale
    o.resetMultiFilterPrefetch()
}
for {
    // drop prefetched seqs now behind the cursor
    for o.mfidx < len(o.mfseqs) && o.mfseqs[o.mfidx] < o.sseq { o.mfidx++ }
    if o.mfidx >= len(o.mfseqs) {           // refill: the search, done once per ~256 msgs
        n, last, err := store.LoadNextMsgsMulti(o.filters, o.sseq, 256, &o.mfseqs)
        if n == 0 { return nil, last, err }  // EOF, same as before
    }
    seq := o.mfseqs[o.mfidx]; o.mfidx++; o.mflast = seq
    sm, err := store.LoadMsg(seq, smp)        // fresh body load
    if err != nil { o.sseq = seq + 1; continue } // removed since prefetch → skip
    return sm, seq, nil
}

The buffer is invalidated whenever it could be stale: a backward cursor move (redelivery), or a change to the consumer's filter set (handled in updateConfig). Forward cursor jumps are safe — stale-but-still-ahead sequences are simply dropped and the buffer refills.

05Why it helps — the complexity

Let M = messages delivered, F = filter subjects, S = distinct subjects in a block. The search cost per call is roughly proportional to the subject-tree intersection it performs.

PathSearch costPer delivered messageTotal over a delivery
Before — per message ~O(S) intersect 1 full search O(M · search)
After — batched ~O(S) intersect 1 LoadMsg + 1/256 search O(M + (M/256)·search)

The search term doesn't get cheaper — it gets amortized by ~256×. The per-message cost drops to a plain sequence lookup, which is independent of F. That's why the "after" line in the chart below is flat across filter counts while the "before" line climbs.

07Correctness — what was preserved

Fresh bodies. Messages are loaded by sequence at delivery time, never from a stale prefetch. A message removed after prefetch fails its LoadMsg and is skipped.
Redelivery / rewind. If the cursor moves back to or below the last sequence served, the buffer is discarded and rebuilt from the new position.
Filter changes. updateConfig resets the buffer whenever the consumer's subject filters change, so old matches are never served under a new filter.
EOF & skip accounting. The helper returns the same (nil, lastSeq, ErrStoreEOF) contract as before, so cursor advancement, updateSkipped for replicas, and num-pending math are unchanged.

Validated across all store permutations and the multi-filter, pull-consumer and work-queue consumer suites, including under the Go race detector.

08Known limitations & next steps

  • Interior block skipping. Empty interior blocks are still skipped only on the first probed block (the pre-existing psim design). Tracking all blocks per subject (a "v2" psim) would let very sparse streams skip empty interior blocks per batch too.
  • Adaptive selectivity. When a filter set matches most of the stream, deliberately fall back to a contiguous unfiltered scan with an inline interest test — formalizing the "just drop the filter" instinct, but without shipping non-matching messages over the wire.
  • Prefetch depth. The batch size is a fixed 256; it could be tuned to the pull request's own batch size / max-bytes.
