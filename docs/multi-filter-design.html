Scaling multi-subject filters for consumers

Why consumers filtering on 10–90+ subjects fell off a cliff, and the design that makes per-message delivery cost independent of the filter count — by doing the multi-subject search once per batch instead of once per message.

Status  Implemented Phase 1 Phase 3 Phase 2 partial Phase 4·5 proposed

1Summary

JetStream consumers that filter on many subjects performed a full multi-subject search once per delivered message. That search cost grows with the number of filter subjects, so delivery scaled like messages × filters. In bad cases it was faster to remove the filter, ship everything, and filter on the client.

This design amortizes the search across a batch. A new store API, LoadNextMsgsMulti, runs the search once and returns up to N matching sequence numbers; the consumer prefetches a batch and serves them with cheap by-sequence reads. Per-message cost becomes independent of the filter count.

2Background & problem

The delivery loop loopAndGatherMsgs pulls one message per iteration via getNextMsg. For a multi-filtered consumer that meant one store call — LoadNextMsgMulti — per message. Each call re-acquired the store lock, re-selected the starting block, and walked the per-block subject tree (fss) intersected against the filter sublist (IntersectGSL) — just to find the single next match.

The bottleneck. That intersection is the part whose cost rises with the filter count and the block's subject cardinality. Performed per message, total work became messages × search instead of messages.

The mem store was worse — its multi-filter lookup was an explicit "simple linear walk to get started" with no subject-index acceleration, degrading toward O(M²) for sparse matches.

Why "drop the filter" won. The unfiltered path is a contiguous sequential scan — cache-friendly, no tree intersection. The multi-filter path paid the intersection tax on every message. The goal is to make the server do the smart thing without that tradeoff.

3Goals & non-goals

Goals

  • Per-message cost independent of the number of filters.
  • No change to delivery semantics, ordering, ack/redelivery, or freshness.
  • Never materially worse than the unfiltered baseline.
  • Change isolated to the multi-filter path (o.filters != nil).

Non-goals (this phase)

  • Single-filter / unfiltered paths.
  • Eliminating the tree intersection entirely → Phase 2.
  • Interior-block skipping for very sparse streams → Phase 5.
  • Any client / protocol change — purely server-internal.

4Design overview

Decouple searching (expensive, amortizable) from reading (cheap, per-message):

getNextMsg
→
prefetch buffermatching seqs
→
LoadMsg(seq)fresh, per message
buffer empty?
→
LoadNextMsgsMultithe search · once per ~256 msgs

In steady state, delivering a message costs one by-sequence LoadMsg — the same as the unfiltered baseline. The search runs roughly once per 256 messages.

Prefetch sequences, not bodies. A buffered body could be delivered stale if the message was acked/removed in the meantime. Buffering only sequence numbers keeps body loads lazy and fresh; a removed sequence fails its LoadMsg and is skipped. NATS sequences are immutable, so a buffered sequence can never resolve to a different message.

5Detailed design

5.1 — Store API (store.go)

// Append up to maxSeqs matching sequences (ascending) at/after start to *seqs.
// Returns count appended, last sequence considered, ErrStoreEOF when none remain.
func LoadNextMsgsMulti(sl *gsl.SimpleSublist, start uint64,
        maxSeqs int, seqs *[]uint64) (n int, last uint64, err error)

The *[]uint64 is caller-owned and reused across refills to avoid per-batch allocation.

5.2 — File store (filestore.go)

  • LoadNextMsgsMulti reuses the psim first-block skip, then iterates blocks calling msgBlock.collectMatchingMulti until maxSeqs or EOF; on a first-block miss it skips leading empty blocks via checkSkipFirstBlockMulti.
  • collectMatchingMulti is the batched counterpart of firstMatchingMulti: a single sequential pass over the block that appends every matching sequence — one scan yields many matches instead of one.

5.3 — Mem store (memstore.go)

  • nextMultiMatchLocked intersects the sublist against ms.fss to compute [fseq, lseq] bounds (lowest matching First ≥ start, highest Last).
  • shouldLinearScanMulti mirrors the single-filter heuristic — skip the tree walk when the scan range is small relative to subject count.
  • LoadNextMsgMulti now narrows via these bounds (was a naive linear walk); the batched LoadNextMsgsMulti shares the narrowing.

5.4 — Consumer (consumer.go)

New per-consumer state mfseqs / mfidx / mflast and multiFilterPrefetch = 256. getNextMultiFiltered replaces the per-message call and mirrors LoadNextMsgMulti's exact return contract, so the surrounding delivery, skip and num-pending logic is untouched:

if o.sseq <= o.mflast {            // rewound (e.g. redelivery) → buffer stale
    o.resetMultiFilterPrefetch()
}
for {
    for o.mfidx < len(o.mfseqs) && o.mfseqs[o.mfidx] < o.sseq { o.mfidx++ }
    if o.mfidx >= len(o.mfseqs) {            // refill: the search, once per ~256 msgs
        n, last, err := store.LoadNextMsgsMulti(o.filters, o.sseq, 256, &o.mfseqs)
        if n == 0 { return nil, last, err }   // EOF, identical to before
    }
    seq := o.mfseqs[o.mfidx]; o.mfidx++; o.mflast = seq
    sm, err := store.LoadMsg(seq, smp)         // fresh body load
    if err != nil { o.sseq = seq + 1; continue } // removed since prefetch → skip
    return sm, seq, nil
}

resetMultiFilterPrefetch is also called from updateConfig whenever the filter set changes.

6Why it scales

Let M = messages, F = filter subjects, S = distinct subjects per block. The search cost per call is roughly ~O(S) — independent of how many filters express it, but rising with subject cardinality.

PathPer delivered messageTotal over a delivery
Before — per message1 full searchO(M · search)
After — batched1 LoadMsg + 1/256 searchO(M + (M/256)·search)

The search is not made cheaper — it is amortized ~256× out of the per-message path, which collapses to a by-sequence read whose cost is independent of F.

10Risks & rollout

  • Timing-test flakiness. The scaling test asserts a wall-clock comparison; margin is >10× and it passed CI, but if it ever flakes, switch the assertion to operation counts (search invocations / lock acquisitions) rather than time.
  • Memory. ~2 KB prefetch buffer per multi-filter consumer, reused across refills.
  • Scope. All changes gated on o.filters != nil; single-filter and unfiltered consumers are unaffected.
  • Rollout. No config flag or protocol change — identical from the client's perspective, only faster.

11Future work

See PHASES.md for detailed, code-referenced plans.

Phase 2 — cached intersection

Cache the matched-subject set keyed by a psim generation counter (or a persistent store-side iterator) to skip the per-refill tree intersection on high-cardinality streams.

Phase 4 — adaptive selectivity

Estimate match fraction from psi.total; pick a contiguous post-filter scan when non-selective. Tune prefetch depth to the pull request batch size.

Phase 5 — interior-block skipping

Track per-subject block membership in psim for interior skips on every block; optional (nextSeq, subject) min-heap for O(log F) steady state.

Suggested order

4 → 2 → 5. Phase 4 is cheapest and highest value; Phase 5 is largest and only if profiling shows interior sparseness still dominates.
