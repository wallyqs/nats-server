01Two phases of a consumer's life

Every consumer interacts with the store in two distinct ways. First, exactly once when it starts (or fails over to a new leader), selectStartingSeqNo() decides the starting stream sequence o.sseq. Depending on the policy this is either free (read cached StreamState) or an actual search. Then, for the rest of its life, the delivery loop loopAndGatherMsgs → getNextMsg() pulls one message at a time from o.sseq forward.

02Phase 1 — startup seek, routed by policy

This is the only place DeliverPolicy changes which store method is called. Several policies do no search at all — they read the already‑maintained StreamState. The expensive ones are DeliverLastPerSubject (calls MultiLastSeqs), filtered DeliverLast (calls FilteredState once per filter), and DeliverByStartTime (calls GetSeqFromTime, plus a FilteredState per filter to close the gap).

03Phase 2 — steady‑state, routed by filter shape

Once running, the policy no longer matters — getNextMsg() dispatches purely on filter shape and on whether the message is a fresh delivery or a redelivery. In 2.12.10 the multi‑filter branch calls LoadNextMsgMulti once per delivered message:

// server/consumer.go — getNextMsg() in v2.12.10
filters, subjf, fseq := o.filters, o.subjf, o.sseq
if filters != nil {
    sm, sseq, err = o.mset.store.LoadNextMsgMulti(filters, fseq, &pmsg.StoreMsg) // ← per message
} else if len(subjf) > 0 {
    sm, sseq, err = o.mset.store.LoadNextMsg(filter, wc, fseq, &pmsg.StoreMsg)
} else {
    sm, sseq, err = o.mset.store.LoadNextMsg(_EMPTY_, false, fseq, &pmsg.StoreMsg)
}
Key separation. A DeliverLastPerSubject consumer pays its cost at startup in MultiLastSeqs and then serves the seeded sequences with cheap LoadMsg calls (the skip‑list). Its steady‑state tail — anything published after it started — falls into the normal multi/single/none branch above.

What the LastPerSubject skip‑list actually is

The "skip‑list" (o.lss, type lastSeqSkipList) is not the classic probabilistic skip‑list data structure — it is a tiny precomputed delivery plan: a flat sorted slice of sequences plus a resume watermark. DeliverLastPerSubject means "for every matching subject, deliver only that subject's last message, then tail normally." Instead of scanning for those, the consumer asks the store for all of them up front and replays them by sequence:

type lastSeqSkipList struct {
    resume uint64   // stream LastSeq captured at creation — where normal tailing resumes
    seqs   []uint64 // last seq of each matching subject, ascending (from MultiLastSeqs)
}

lss := &lastSeqSkipList{resume: state.LastSeq}
lss.seqs, _ = o.mset.store.MultiLastSeqs(filters, 0, 0) // one search, N results
o.lss = lss

From then on, getNextMsg checks hasSkipListPending() before the filter dispatch and drains the plan one entry at a time — popping seqs[0], pointing o.sseq at it, and doing a plain by‑sequence LoadMsg (no search, no filtering — membership was decided when the list was built). When the last entry is popped it jumps o.sseq to resume, clears the list, and calls updateSkipped. The expensive part is the single MultiLastSeqs search that built it (§5); the list itself holds an O(N) slice and is rebuilt on every leader failover.

05Worst case — multi‑filter delivery (LoadNextMsgMulti per message)

This is the dominant throughput cost in 2.12.10. Every delivered message re‑enters the store and re‑runs the whole multi‑subject search: re‑acquire the store lock, re‑select the starting block, and re‑walk the per‑block fss subject‑tree intersected against the filter sublist (IntersectGSL / firstMatchingMulti) to find the single next match. Cost rises with the number of filter subjects, so a delivery scales like messages × filters.

memstore is worse. In 2.12.10 the memory store's LoadNextMsgMulti is an explicit "simple linear walk to get started" (TODO(dlc)): it scans every sequence from the cursor to LastSeq running HasInterest per message, with no fss subject‑index narrowing. For a sparse multi‑filter delivery that approaches O(M²) across the whole delivery — each of the M deliveries can rescan a large suffix of the stream.

06Worst case — MultiLastSeqs (DeliverLastPerSubject startup)

This is the heaviest startup path. The fast lane is taken only when the filter set is "all" (filterIsAll) with no caps — then allLastSeqs reads the answer from resident state. Otherwise it walks blocks backwards from the last block, loading each block's fss, ticking matched subjects off as it finds their last sequence, and stops only when every matched subject is accounted for.

memstore footgun. In memStore.MultiLastSeqs, the "ss.Last > maxSeq" branch runs for seq := maxSeq; seq > 0; seq--, a linear walk to sequence 1 for each such subject. The common consumer call uses maxSeq = 0 (implied = LastSeq), which avoids it.

07Under the hood — data structures & I/O

The startup‑heavy methods all work the same way at the bottom: they consult in‑memory indices first and only touch the disk when they must materialise a block to read subjects or message timestamps. On the memory store none of this involves syscalls — every structure below is a Go map or an in‑memory subject tree.

The one I/O primitive. Every "block read" above is the same pipeline: acquire the global dios semaphore (bounding concurrent disk ops server‑wide), open + fstat + ReadFull the .blk file, then in‑process decrypt (if encrypted) and decompress (if S2). Once resident, the block's fss/cache serve subsequent calls for free until CacheExpire evicts them. The memory store has none of this layer — its worst cases are CPU/lock‑bound map walks, never syscalls.
