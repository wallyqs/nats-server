Store access paths by DeliverPolicy

Which store method a JetStream consumer calls — and when — depends on its DeliverPolicy and its filter shape. This map separates the one‑time startup lookup from the per‑message steady‑state loop, names the method each path takes on both the file and memory stores, and pins the input shapes that make each one fall off a performance cliff.

01Two phases of a consumer's life

Every consumer goes through two distinct interactions with the store. First, exactly once when it starts (or fails over to a new leader), selectStartingSeqNo() decides the starting stream sequence o.sseq. Depending on the policy this is either free (read cached StreamState) or an actual search. Then, for the rest of its life, the delivery loop loopAndGatherMsgs → getNextMsg() pulls one message at a time from o.sseq forward.

02Phase 1 — startup seek, routed by policy

This is the only place DeliverPolicy changes which store method is called. Several policies do no search at all — they read the already‑maintained StreamState. The expensive ones are DeliverLastPerSubject (calls MultiLastSeqs), filtered DeliverLast (calls FilteredState once per filter), and DeliverByStartTime (calls GetSeqFromTime, plus a FilteredState per filter to close the gap).

03Phase 2 — steady‑state, routed by filter shape

Key separation. A DeliverLastPerSubject consumer pays its cost at startup in MultiLastSeqs and then serves the seeded sequences with cheap LoadMsg calls (the skip‑list). Its steady‑state tail — anything published after it started — falls into the normal multi/single/none branch above. So the recent interior‑skip work helps that tail, not the initial last‑per‑subject burst.

05Worst case — MultiLastSeqs (DeliverLastPerSubject startup)

This is the heaviest startup path. The fast lane is taken only when the filter set is "all" (filterIsAll) and there is no maxSeq/maxAllowed — then allLastSeqs reads the per‑subject index directly. Otherwise it walks blocks backwards from the last block, loading each block's fss, ticking matched subjects off as it finds their last sequence, and stops only when every matched subject is accounted for.

memstore footgun. In memStore.MultiLastSeqs, the "ss.Last > maxSeq" branch runs for seq := maxSeq; seq > 0; seq--, a linear walk all the way to sequence 1 for each such subject. With a low maxSeq and many sparse subjects this is O(maxSeq · S) — the single most quadratic path in this map. The common consumer call uses maxSeq = 0 (implied = LastSeq), which avoids it.

06Worst case — LoadNextMsgsMulti (multi‑filter steady state)

The batched path searches once per 256 matches and skips runs of non‑matching blocks via the position‑aware checkSkipInteriorBlocksMulti. It stays flat when matched subjects are localized to regions of the stream. The residual worst case is a matched subject that spans the gap: because psi records only first/last block per subject, an interior block of a spanning subject can't be proven empty, so the scan walks it block by block.

Also worst for batched multi: very high‑cardinality streams. When psim.Size() > 1,000,000 the interior skip bails out (the psim walk would cost more than it saves), so gaps are scanned. The same threshold gates the legacy first‑block skip.
Best for batched multi: matches spread fairly evenly across blocks. There is little to skip and the amortized search (once per 256 deliveries) collapses per‑message cost to a by‑sequence LoadMsg — independent of the filter count.

Reading this map operationally. Startup cost is paid once per consumer (and once per leader failover, since selectStartingSeqNo re‑runs). Steady‑state cost is paid per delivered message forever. So a heavy MultiLastSeqs hurts consumer creation latency and failover, whereas a heavy multi‑filter search hurt throughput — which is why the delivery path was the one batched first.
