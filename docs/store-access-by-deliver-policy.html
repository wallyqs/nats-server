Store access paths by DeliverPolicy

Which store method a JetStream consumer calls — and when — depends on its DeliverPolicy and its filter shape. This map separates the one‑time startup lookup from the per‑message steady‑state loop, names the method each path takes on both the file and memory stores, and pins the input shapes that make each one fall off a performance cliff.

01Two phases of a consumer's life

Every consumer goes through two distinct interactions with the store. First, exactly once when it starts (or fails over to a new leader), selectStartingSeqNo() decides the starting stream sequence o.sseq. Depending on the policy this is either free (read cached StreamState) or an actual search. Then, for the rest of its life, the delivery loop loopAndGatherMsgs → getNextMsg() pulls one message at a time from o.sseq forward.

02Phase 1 — startup seek, routed by policy

This is the only place DeliverPolicy changes which store method is called. Several policies do no search at all — they read the already‑maintained StreamState. The expensive ones are DeliverLastPerSubject (calls MultiLastSeqs), filtered DeliverLast (calls FilteredState once per filter), and DeliverByStartTime (calls GetSeqFromTime, plus a FilteredState per filter to close the gap).

03Phase 2 — steady‑state, routed by filter shape

Once running, the policy no longer matters — getNextMsg() dispatches purely on filter shape and on whether the message is a fresh delivery or a redelivery. There are four sub‑paths:

Before / after — the multi‑filter branch vs release/v2.12.10

The only line that changed on this hot path is the multi‑filter dispatch in getNextMsg:

// release/v2.12.10 — one full multi‑subject search per delivered message
sm, sseq, err = o.mset.store.LoadNextMsgMulti(filters, fseq, &pmsg.StoreMsg)

// this branch — search amortized across a prefetch batch (once / 256), then by‑seq reads
sm, sseq, err = o.getNextMultiFiltered(&pmsg.StoreMsg)
release/v2.12.10 · multi‑filter delivery cost was O(M·F): every delivered message re‑ran the full multi‑subject search (re‑lock, re‑select block, re‑walk the fss×sublist intersection). At 90 filters over 200k messages that was ~3.5 s and ~18,001 searches; allocations climbed into the millions. On a sparse/clustered stream it could not skip the gap, scaling with the gap size.
this branch · getNextMultiFiltered prefetches up to 256 matching sequences per search and serves them with by‑seq LoadMsg, so per‑message cost is independent of F. Same 90‑filter delivery: ~24 ms, 72 searches. Position‑aware interior skipping (§6) keeps sparse/clustered streams flat too — ~13 KB/op vs ~2.3 MB/op at a 100k‑message gap.
Key separation. A DeliverLastPerSubject consumer pays its cost at startup in MultiLastSeqs and then serves the seeded sequences with cheap LoadMsg calls (the skip‑list). Its steady‑state tail — anything published after it started — falls into the normal multi/single/none branch above. So the recent interior‑skip work helps that tail, not the initial last‑per‑subject burst.

What the LastPerSubject skip‑list actually is

The skip‑list (o.lss, type lastSeqSkipList) is a tiny precomputed delivery plan built once at startup. DeliverLastPerSubject means "for every subject the consumer matches, deliver only that subject's last message, then tail normally." Rather than scan the stream looking for those messages, the consumer asks the store for all of them up front and replays them by sequence:

type lastSeqSkipList struct {
    resume uint64   // stream LastSeq captured at creation — where normal tailing resumes
    seqs   []uint64 // last seq of each matching subject, ascending (from MultiLastSeqs)
}

// startup (selectStartingSeqNo):
lss := &lastSeqSkipList{resume: state.LastSeq}
lss.seqs, _ = o.mset.store.MultiLastSeqs(filters, 0, 0) // one search, N results
o.lss = lss

From then on, getNextMsg checks hasSkipListPending() before the filter dispatch and drains the plan one entry at a time — popping seqs[0], pointing o.sseq at it, and doing a plain by‑sequence LoadMsg (no search, no filtering — the membership was already decided when the list was built):

Two consequences worth noting: the list is materialised eagerly, so a consumer matching a very large number of subjects holds an O(N) sequence slice and pays the full MultiLastSeqs cost before its first delivery; and because it is rebuilt whenever selectStartingSeqNo re‑runs, a leader failover re‑pays that build. The resume watermark guarantees no message published after creation is missed and none of the last‑per‑subject seeds are served twice.

05Worst case — MultiLastSeqs (DeliverLastPerSubject startup)

This is the heaviest startup path. The fast lane is taken only when the filter set is "all" (filterIsAll) and there is no maxSeq/maxAllowed — then allLastSeqs reads the per‑subject index directly. Otherwise it walks blocks backwards from the last block, loading each block's fss, ticking matched subjects off as it finds their last sequence, and stops only when every matched subject is accounted for.

memstore footgun. In memStore.MultiLastSeqs, the "ss.Last > maxSeq" branch runs for seq := maxSeq; seq > 0; seq--, a linear walk all the way to sequence 1 for each such subject. With a low maxSeq and many sparse subjects this is O(maxSeq · S) — the single most quadratic path in this map. The common consumer call uses maxSeq = 0 (implied = LastSeq), which avoids it.

06Worst case — LoadNextMsgsMulti (multi‑filter steady state)

The batched path searches once per 256 matches and skips runs of non‑matching blocks via the position‑aware checkSkipInteriorBlocksMulti. It stays flat when matched subjects are localized to regions of the stream. The residual worst case is a matched subject that spans the gap: because psi records only first/last block per subject, an interior block of a spanning subject can't be proven empty, so the scan walks it block by block.

Also worst for batched multi: very high‑cardinality streams. When psim.Size() > 1,000,000 the interior skip bails out (the psim walk would cost more than it saves), so gaps are scanned. The same threshold gates the legacy first‑block skip.
Best for batched multi: matches spread fairly evenly across blocks. There is little to skip and the amortized search (once per 256 deliveries) collapses per‑message cost to a by‑sequence LoadMsg — independent of the filter count.

Reading this map operationally. Startup cost is paid once per consumer (and once per leader failover, since selectStartingSeqNo re‑runs). Steady‑state cost is paid per delivered message forever. So a heavy MultiLastSeqs hurts consumer creation latency and failover, whereas a heavy multi‑filter search hurt throughput — which is why the delivery path was the one batched first.

08Under the hood — data structures & I/O

The three startup‑heavy methods (FilteredState, MultiLastSeqs, GetSeqFromTime) all work the same way at the bottom: they consult in‑memory indices first and only touch the disk when they must materialise a block to read subjects or message timestamps. Understanding which index each one walks — and what triggers a block read — is the whole performance story. On the memory store none of this involves syscalls: every structure below is a Go map or an in‑memory subject tree.

FilteredState(sseq, subj) — first/last/count for one subject

File store. Two regimes. When sseq == FirstSeq (the common "from the start" call), it takes the numFilteredPending shortcut: read totals and block bounds straight from the resident psim (a Find for a literal, a Match walk for a wildcard) and then touch just the first candidate block's fss to pin the exact First sequence — usually one lazy block load at most. For an arbitrary sseq, it instead loops every block with last.seq ≥ sseq, calling filteredPending → ensurePerSubjectInfoLoaded on each — so a cold scan is one block read + decode per non‑skipped block, plus a possible recalculateForSubj (a bounded in‑block re‑scan) when a subject's First/Last is marked stale. Mem store. Pure in‑memory: walks the ms.fss subject tree and the ms.msgs map; no syscalls. (It takes the write lock because it may refresh the shared SimpleState in place.)

MultiLastSeqs(filters, maxSeq, maxAllowed) — last seq per matching subject

File store. Fast lane: if the filter set is "all" with no caps, allLastSeqs reads the answer from resident state with no block walk. Otherwise it Matches each filter against psim to collect the candidate subject set (and their lblk), then walks blocks backward from the last, calling ensurePerSubjectInfoLoaded (lazy fss ⇒ possible block read) and ticking subjects off as their last sequence is found, stopping once the set is empty. Two things make it expensive: (1) a matched subject whose last lives far back forces the backward walk to load many blocks' fss; (2) when a subject's recorded last exceeds maxSeq, it falls to a per‑subject backward cacheLookup scan inside the block, which requires the full cache (a block read + decode). Mem store. Match over ms.fss per filter; the ss.Last > maxSeq branch degrades to a linear for seq:=maxSeq; seq>0; seq-- walk over the ms.msgs map — quadratic, but no syscalls.

GetSeqFromTime(t) — first seq at/after a timestamp

File store. Cheapest of the three. selectMsgBlockForStart does a binary search over fs.blks comparing each block's resident last.ts (no I/O), narrowing to a single block; then a binary search by sequence within that one block via fetchMsgNoCopyLocked, which pulls the block's cache — at most one lazy block read + decode. Interior deletes (dmap) force a small off++ linear probe around each binary‑search midpoint. Mem store. Same binary‑search shape directly over the ms.msgs map on each message's .ts; no syscalls.

The one I/O primitive. Every "block read" above is the same pipeline: acquire the global dios semaphore (bounding concurrent disk ops server‑wide), open + fstat + ReadFull the .blk file, then in‑process decrypt (if encrypted) and decompress (if S2). Once resident, the block's fss/cache serve subsequent calls for free until CacheExpire evicts them — so the second consumer over the same hot data pays no I/O. The memory store has none of this layer: its worst cases are CPU/lock‑bound map walks, never syscalls.
